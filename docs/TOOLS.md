# Rust MCP tool reference

**As of the issue #9 first-writes branch (draft, stacked on #8 gating):** One diagnostic tool and sixteen **experimental read** Outlook Classic tools (six mail/folder/thread, seven contacts/categories/rules/out-of-office, and three calendar/task reads) and four gated **modify** tools (mark, categorize, create folder, move), four task/event write tools (create/complete task, create/update event), two confirmed **delete** tools (mail, event), a confirmed `outlook_toggle_rule`, a confirmed `outlook_respond_event`, and `outlook_check_action`, and five **send-pipeline** tools (send, reply, forward, send draft, check send), which only send in server mode `full` after the user approves a preview. Modify tools are refused unless the server runs with `OUTLOOK_MCP_MODE=full` and `modify` is not denied are registered in `rust/src/lib.rs`. This inventory is grounded in `rust/src/contracts.rs`; it is not a live Outlook verification.

All mail list/search/thread messages should return compact in-memory `entry_id` handles such as `m1` rather than raw EntryIDs/StoreIDs. Handles expire on restart and may be evicted; repeat search/list when `outlook_get_mail` says a reference is unknown. Raw IDs can still be supplied for compatibility but **do not share them in issues**.

## Example call sequence (for a trusted test profile)

1. Start the MCP server with no command-line flags; connect an MCP Inspector or test client.
2. Invoke `outlook_rust_status`; it only reports static capability flags.
3. Invoke `outlook_whoami`; verifies Outlook COM access.
4. Invoke `outlook_search_mails` with `{"query":"test","scope":"subject","limit":10,"backend":"legacy"}` using a **safe test query**.
5. Select a result's `entry_id` and invoke `outlook_get_mail` with `{"entry_id":"m1","max_body_chars":1000}`.
6. Optionally call `outlook_get_thread` with `{"entry_id":"m1","max_messages":5,"per_message_chars":500,"total_body_chars":2000}`. This depends on actual store conversation support.

Do not assume sample `m1` exists: use the handle returned in *your* current MCP session. A tool response may contain confidential mail; never paste it into GitHub.

## Search semantics worth knowing

- `scope=subject_body` may select `Items.Restrict` in auto mode; `table` mode explicitly rejects body search.
- `backend=indexed` is opt-in, requires an Outlook Instant Search-enabled store and event delivery; no performance claim yet.
- Mail `received` (and `sent` in threads) are ISO-8601 local time with a UTC offset (`2026-11-03T13:03:54-05:00`), or `null` when unset. They replace the old `received_local` locale text, matching Python's `received`. `from_address` is the SMTP address; for Exchange-internal senders it comes from PR_SENDER_SMTP_ADDRESS, and is empty only if Outlook cannot supply one.
- Returned `has_more` / `scan_truncated` are not proof all mailbox results have been checked.
- No `outlook_send_mail`, delete, move, calendar writes, file saves, or similar Rust mutation tools are registered.

For the **existing Python** 31-tool inventory, consult [`rust/compatibility/tools.md`](../rust/compatibility/tools.md). That list is a migration target, not the number of currently implemented Rust tools.


## MCP Apps views (issue #10, draft)

The server declares the `resources` capability and serves the Python server's five views (`src/outlook_mcp/ui/`, one shared copy) as `ui://outlook/{mail-list,mail-view,calendar,contacts,tasks}.html` with MIME `text/html;profile=mcp-app`. `outlook_list_mails` and `outlook_search_mails` link `mail-list`, `outlook_get_mail` links `mail-view`, `outlook_list_events` links `calendar`, `outlook_list_contacts` and `outlook_search_contacts` link `contacts`, `outlook_list_tasks` links `tasks` through `_meta.ui.resourceUri`. Those tools also return the same JSON as `structuredContent`; mail results gain a `received` field (ISO local time when Outlook's text has the `yyyy/mm/dd:hh:mm:ss` shape, else the text unchanged) next to `received_local`. Clients without MCP Apps support ignore all of this.

**Known gaps:** Rust mail results have no `flagged`, `has_attachments`, `preview` or `attachments`, so those parts of the mail views stay empty. Buttons in the views call tools back; write tools in them still need server mode `full` and the approval window. **Rendering:** the calendar view (`outlook_list_events`) was seen rendering as a widget, with today's and upcoming events grouped by day, in the owner's Claude client on 2026-11-02 (screenshot; the owner reports it was the Claude Code side). The mail list, mail reader, contacts and tasks views have not been opened, and the view buttons were not clicked. Protocol level (capability, tool metadata, resource list and read, `structuredContent`) was also checked with a script.
